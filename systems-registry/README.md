# systems-registry

A tool for auto-detecting and documenting **complex systems** in this
repo — coordinated multi-file pipelines whose pieces span disjoint
directories and whose loops close back into something. Sister tool to
`tools/docgen/`: docgen documents *directories*, systems-registry
documents *systems*.

If you've never seen the design doc, read
`docs/superpowers/specs/2026-05-25-systems-registry-design.md` first.

## Quickstart

```
node tools/systems-registry/cli.mjs detect      # list detected systems
node tools/systems-registry/cli.mjs scaffold --all  # write skeleton manifests
node tools/systems-registry/cli.mjs status      # list active registered systems
node tools/systems-registry/cli.mjs view        # render Mermaid diagrams in a local browser
node tools/systems-registry/cli.mjs build       # emit a static GitHub Pages site
```

`view` spins up a tiny local server (picks a free port, opens your
browser) with a sidebar nav across all registered systems, the
composite cross-system diagram at top, and each system's loop diagram
+ body rendered inline via `mermaid.js`. Files are read from disk on
every request — edit a manifest, refresh, see the new diagram. No
build, no deploy, no npm install. Pass `--no-open` to skip the browser
auto-launch.

`build` emits a static, self-contained site at `dist/systems/index.html`.
Same layout as `view`, pre-rendered. CI runs this on every push to main
(see `.github/workflows/systems-pages.yml`) and deploys to your repo's
GitHub Pages site (`https://<org>.github.io/<repo>/`).

> One-time setup after this lands on main: enable Pages in repo
> settings → "Build and deployment" → **Source: GitHub Actions**.
> Until then the workflow will run successfully but the deploy step
> will be skipped/error and nothing will be live.

After scaffolding, fill in the body of each `docs/systems/<name>.md`
(Mermaid diagram + anchors + invariants + failure modes + where to
start reading) and flip `status: draft` → `status: active` in the
front-matter.

The PreToolUse inject hook is wired in `.claude/settings.json` and
fires automatically — no install step. The next Claude turn that touches
a file matching any system's globs will see the matching system's
Mermaid + page link injected as context.

## What gets detected

Each candidate dir is scored against 8 signals. ≥4 qualifies. See the
spec for the full list; the high points:

- **Coordinator** — top-level file imports ≥2 siblings
- **Persistent state** — writes JSON/MD/state across invocations
- **Loop** — `while True`, `--until-done`, `*_loop.py`, etc.
- **Subprocess spawn** — `spawn`, `execFile`, `playwright`, `claude -p`
- **Hook** — registered in `.claude/settings.json`, git hooks, npm lifecycle
- **Cross-tree refs** — imports from ≥2 other top-level dirs
- **Coordinated tests** — ≥3 test files
- **Hand-written README or spec** — non-docgen marker, or matching spec

A directory scoring ≥4 with >50 source files is treated as a federation
and decomposed one level deeper.

## The closing arrow

The point of this tool is to close the loop back into Claude. When you
edit `services/api/workflow/shortlist.ts`, the inject hook matches
that path against every system's globs, finds `request-pipeline`
(globs include `services/api/workflow/**`), and emits its Mermaid +
page link to stdout. Claude Code feeds hook stdout into the next LLM
turn as additional context — so the next time Claude reasons about
that file, it already has the full pipeline diagram and stage gates
loaded, without having to Read anything explicitly.

Dedup is per-session via `/tmp/systems-registry-injected-<sid>.json`,
so the same system page isn't re-emitted on every Read in a file it
already covered.

## Validate + refine (LLM-as-judge quality loop)

Pass 2.5 (`vet`) does cheap structural checks. `validate` is the deeper
judge: it scores a generated manifest **0-10** on four dimensions —
correctness, completeness, sizing, clarity — against the *actual anchor
source*, and returns a verdict (`ship` / `revise` / `split`) plus
concrete edits.

```
# score one system (runs the judge)
node tools/systems-registry/cli.mjs validate --target billing-engine

# see EXACTLY what gets sent — prompt + command, nothing runs
node tools/systems-registry/cli.mjs validate --target billing-engine --dry-run

# machine-readable
node tools/systems-registry/cli.mjs validate --target billing-engine --json
```

`validate` exits non-zero when `overall < 7`, so it doubles as a CI gate.

### Refine — iterate to a target score

```
node tools/systems-registry/cli.mjs refine --target billing-engine \
  --min-score 7 --max-rounds 2
```

Defaults: `--min-score 7`, `--max-rounds 2`. `overall` is a weighted
average of the four dimensions kept to one decimal.

**Why the bar is 7, not higher.** The hard cap pins ANY doc with a
findable defect to ≤7. A strict judge almost always finds *something*,
so 7 is effectively the ceiling for real auto-generated docs — a bar of
8.5 is unreachable and makes refine loop uselessly to max rounds every
time (learned the hard way on a full sweep: 30/30 systems capped ≤7,
none cleared 8.5). So the gate is 7: a doc passes once it's "clean
enough to only have minor nits" (weighted ≥7 → capped to 7 → pass), and
genuinely deficient docs (weighted <7 — e.g. a 2.1 with fabricated
flows) fail and get refined or flagged needs-review. Set `--min-score 9`
explicitly if you want a flawless-only bar (expect most docs to fail it).

Loops **generate → validate → regenerate-with-feedback** until the score
clears `--min-score`, the round budget runs out, or the verdict is
`split` (a structural call a human must make — the loop won't try to
fix "this should be N systems" by rewording). Each regen receives the
judge's `issues` / `missing` / `suggestions` as the highest-priority
instruction.

### Choosing the judge model (claude / codex / gemini)

The default judge is `claude -p` — the only LLM CLI the tool already
depends on, so `validate`/`refine` work out-of-the-box for everyone who
clones the repo. Point `SYSREG_JUDGE_CMD` at any CLI that reads a prompt
on stdin and writes a response to stdout to use a different model:

```
SYSREG_JUDGE_CMD="codex exec"  node tools/systems-registry/cli.mjs validate --target foo
SYSREG_JUDGE_CMD="gemini -p"   node tools/systems-registry/cli.mjs refine   --target foo
```

A *different* model makes a stronger judge — a model is partly blind to
its own generator's systematic errors, so cross-model judging (claude
generates, codex/gemini grades) catches more. The generator stays on
`claude -p`; only the judge swaps. The validation prompt is
self-documenting (the rubric travels inside it) — `--dry-run` prints the
whole thing so you can audit or hand it to any model manually.

## Per-repo context (the cross-repo extension point)

The tool ships canonical and stays repo-agnostic — no consumer-specific
terms, no hard-coded URLs, no embedded domain knowledge. Every consumer repo
that needs to tilt the hypothesis its own way drops a single file:

```
docs/systems/_context.md
```

It's read by Pass 1 (`gatherInputs`) and injected near the **top** of
the hypothesis prompt with a "TRUST THIS over inferences" framing —
above the candidate dump, above the deployment manifest list. If the
file is absent the section is silently omitted, so the canonical tool
behaves identically in repos that haven't authored one yet.

Good content to put in `_context.md`:

- **Domain vocabulary.** What does "engine" / "agent" / "pool" mean
  in your repo? (Cuts the LLM's general-purpose interpretation noise.)
- **Out-of-scope dirs.** *"Anything under `legacy/` is a parked
  rewrite. Don't promote it to a system."*
- **Promotion / merge opinions.** *"Always keep `foo` and `bar` as one
  system."* / *"Never merge `baz` into anything; it has a separate
  on-call."*
- **Known-dormant deployed services.** If `render.yaml` shows a cron
  with a `0 0 31 2 *`-style schedule, say so explicitly.
- **Naming conventions.** *"Our handlers all end in `Handler.ts`; our
  route files end in `Routes.ts`."*

Keep it short — capped at 16 KB. Treat it like a `CLAUDE.md` for the
systems-registry generator, not a design doc.

Repo metadata (title, GitHub URLs in the static viewer) is derived from
`git remote get-url origin` at build time via `repo-meta.mjs`; you don't
need to configure it. A clone with no remote shows the dir basename and
omits source-file links — degrades gracefully.

## Adding a new system

1. Run `node tools/systems-registry/cli.mjs detect` — does the
   directory score ≥4 already? If yes, scaffold and fill in. If no, look
   at which signals are missing.
2. If signals are missing for a system you know IS real: either tune
   the detector (see `detect.mjs`) or hand-author the manifest at
   `docs/systems/<name>.md` with `status: active`.
3. Front-matter must include `name`, `summary`, `globs[]`. Inject
   defaults to `{mermaid: true, page_link: true, cap_bytes: 4096}`.
4. Re-run the test suite to make sure nothing regressed.

## What is NOT in scope

- Auto-regenerating system bodies via `claude -p` — design ready (P2),
  not shipped in v1
- Push-hook auto-refresh — design ready (P2), not shipped
- In-session "you should register this" nudges — design ready (P3),
  not shipped
- Cross-system navigation links (beyond the composite diagram)
- A `.systems-ignore` file

See the spec's "What v2 should ship" section.

## Coexistence with docgen

Both tools register a PreToolUse hook in `.claude/settings.json`. They
coexist cleanly because Claude Code runs every hook in the matcher list
and concatenates their stdouts. Order isn't significant — both are
non-blocking and idempotent.

If you're confused about which tool to use: a per-*directory* summary →
docgen. A per-*system* page with anchors spanning the tree → systems-registry.
